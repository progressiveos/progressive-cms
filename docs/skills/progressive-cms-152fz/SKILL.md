# Progressive CMS: техническая подготовка по 152-ФЗ

Выполни техническую часть задачи на уже работающем сайте. Нужный результат — проверенные настройки и изменения сайта, карта потоков данных и короткий список оставшихся действий владельца. Не выдавай наличие баннера или этого Skill за юридическую сертификацию всего оператора.

## Начало

Установи разрешённые origin, site, environment, доступ к CMS и границы инфраструктурных работ. Используй уже выданные полномочия; не переспрашивай про каждое безопасное изменение в согласованной задаче. Проверь `cms agent bootstrap --json`, фактическую версию/контракты и [manifest.json](manifest.json). Для HTTP используй локальную [карту действий](references/pcms-workflow.md) и [схемы API](references/api-operations.json); MCP выбирай только через discovery. Core и БД не исправляй частными обходами.

До правок прочитай [техническую матрицу](references/technical-controls.md). Проверь действующие положения и редакции по [источникам](references/sources.md) на дату выполнения. Дата подготовки Skill не доказывает актуальность закона в следующем году. Если источник недоступен, используй доступную официальную копию/публикацию и явно укажи, какие изменения не удалось проверить; не объявляй сведения актуальными автоматически.

От владельца нужны факты, а не юридическая работа агента: оператор и контакт для обращений; цели/основания обработки; утверждённые сроки; разрешённые получатели/страны; одобренные тексты/версии политики и согласий. Продолжай независимые технические работы, пока эти данные уточняются. Не сочиняй реквизиты, основания, тексты согласия или утверждение, что уведомление РКН подано.

## Порядок работы

1. **Инвентаризируй сбор и движение.** Все формы/квизы/регистрация/заказ/поиск/чат/вложения, серверные логи, аналитику, CRM/почту/коллтрекинг, карты, видео, шрифты, CAPTCHA, CDN, бэкапы и внешние ИИ-сервисы. Смотри реальный Network/Storage, включая первый визит, а не только репозиторий темы.
2. **Примени выбранную владельцем минимизацию и политику передач.** Удали лишние обязательные поля; убери ПД из URL, событий, логов и ответов. Не подключай внешний сервис только ради красивой страницы или SEO. Не выгружай заявки в инструменты агента.
3. **Настрой основания, формы и информирование.** Размести предоставленные владельцем документы в доступных местах; согласие — отдельное, осознанное действие там, где оно выбрано основанием. Сервер проверяет обязательное согласие, история позволяет восстановить принятую редакцию. Реклама/публикация ПД требуют отдельных решений; не смешивай их с обращением.
4. **Реализуй выбранную политику аналитики.** Владелец выбирает immediate или consent-категории; Core не принуждает consent для всех провайдеров. При выбранном consent-основании предоставь отказ/настройки/отзыв и проверь отсутствие соответствующих bootstrap/loaders/пикселей до разрешения. Раздельные категории, persistence и revoke с reload описаны в [карте действий](references/pcms-workflow.md). Не обещай отмену уже отправленных запросов или управления произвольным GTM-кодом.
5. **Проверь серверную часть.** Фактическое размещение и трансграничные маршруты, права/сессии, безопасную доставку, ограничения загрузок, секреты, очередь/Worker, сроки, удаление и бэкапы. Без инфраструктурных доказательств ставь `BLOCKED`, а не «хостинг российский, значит всё хорошо».
6. **Пройди негативные проверки.** Прямая отправка без требуемого согласия; отказ; разрешена только одна категория; отзыв; JavaScript выключен; сторонний ресурс недоступен; анонимный доступ к синтетической заявке/файлу/экспорту; жизненный цикл удаления синтетических данных. Разрушающие/нагрузочные проверки — только на согласованных тестовых данных/контуре.
7. **Проверь опубликованный результат.** Обновление определения формы/темы не доказывает, что пользователю показывается нужная версия. Проверь реальные страницы и новый визит после изменения. Не принимай обычный HTTP 200 за проверку приватности.

По выбору владельца применяй [адресные инструменты](references/personal-data-tools.md): preview → явное block/unblock/rectify/erase → receipt → действия у получателей. Сохрани request/case IDs и точный body для retry. privacy.manage не нужен обычному site-builder; выдаётся отдельно. Наличие pending/owner_exception не называй успешным удалением внешней копии.

## Граница результата

Владелец отвечает за уведомления РКН (включая отдельную трансграничную процедуру), законность целей/оснований, договоры с обработчиками, юридические документы, назначение ответственных и формальное утверждение профиля защиты. Агент размещает предоставленные тексты и реализует утверждённые технические меры; не подаёт уведомления и не составляет за владельца юридический комплект.

Закрой все **применимые** технические строки матрицы; неприменимость обоснуй. Не ограничивайся выборкой форм, если остальные ещё собирают данные. Если один контур заблокирован, заверши независимые исправления и назови точный блокер. Не подменяй проверку фактического эффекта инструмента неподтверждённой «ручной процедурой». Обычная работа сайта не требует юридического case/receipt; владелец определяет выбранные меры и исключения, агент честно фиксирует результат и пределы проверки.

Заполни [акт технической готовности](assets/acceptance.md): `PASS / FAIL / BLOCKED / N/A`, доказательство без ПД, источник требования, исправление и ответственный. Юридическая часть владельца — отдельный список. Итоговая формулировка: «технические меры проверены в указанном объёме» с открытыми пунктами; «полное соответствие 152-ФЗ» допустимо только как задача, а не автоматический вывод этого Skill.

Если доступны только файлы без целевой CMS/сети, выполни статическую часть и подготовь reviewable изменения; не помечай их применёнными и не ставь PASS серверной/полевой приёмке.
